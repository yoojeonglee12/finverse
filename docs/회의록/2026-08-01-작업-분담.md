# 작업 분담 회의록 — 3트랙 병렬 착수 · 시뮬레이션 분산 프로토타입

- **일시**: 2026-08-01
- **참석자**: 임영진 · 장진우 · 신민수 (개발) · 이유정 (기획/프론트) · 곽동규 (세계관)

> **이 회의의 성격** — 준비된 안건(브리핑 §7의 A/B/C 그룹)을 결정하는 대신, **일단 각자 손을 움직여 착수하는 쪽**으로 방향이 잡혔다. 따라서 아래 §3의 미결 안건은 **부결이 아니라 이월**이다.

## 1. 결정 #20 — 작업 분담: 3트랙 병렬 착수

| 트랙 | 내용 | 담당 |
| --- | --- | --- |
| **① 프론트엔드 랜딩 + 시뮬 연결** | 랜딩 페이지에 **뉴스 수집** 결과를 노출하고, 그 뒷단에 **시뮬레이션을 붙이는** 작업 | 【확인 필요 — 회의 중 명시되지 않음】 |
| **② 데이터 수집 백엔드** | 외부 데이터 연동 · 수집 파이프라인 | **신민수** |
| **③ 가상 트윈 화면 데모 → 프론트 연결** | 나 트윈(V3) 화면 데모를 만들고 **프론트엔드와 엮는** 작업 | **이유정** |

- **①의 담당자가 회의록에 남지 않았다.** 임영진·장진우 중 누구인지(또는 공동인지) 확인해 이 표를 채울 것.
- 세 트랙은 서로를 기다리지 않고 **병렬로 간다.** PRD §7의 4덩어리 중 「배치 파이프라인」이 ②, 「V3 화면」이 ③에 대응하고, ①은 「V1 화면 + 시뮬 생성기」에 걸쳐 있다.

**PRD 모듈과의 대응**

| PRD 모듈 (§7) | 이번 분담 |
| --- | --- |
| 배치 파이프라인 | ② 신민수 |
| 시뮬 생성기 | ① (+ 결정 #21의 분산 프로토타입) |
| 앱 서버 | 【미할당】 — 현재 어느 트랙에도 명시적으로 들어가 있지 않음 |
| V1 시장 인사이트 | ① |
| V3 나 트윈 | ③ 이유정 |

> ⚠️ **앱 서버가 어느 트랙에도 없다.** ①의 "시뮬레이션 붙이는 작업"에 포함된 것으로 보이나 명시되지 않았다. 세 트랙을 나중에 합칠 때 이 조각이 비어 있으면 통합이 막힌다.

## 2. 결정 #21 — 시뮬레이션: 분산 프로토타입 후 통합

**합의되지 않은 것**: 시뮬레이션을 **어떻게 구현할지**에 대해 참석자 간 합의에 이르지 못했다.

**결정**: 방식을 먼저 합의하려 시간을 쓰는 대신, **각자 간단한 최소 버전을 뜯어서 만들어 본 뒤 합친다.**

- 논의로 좁히기 어려운 문제라고 판단 → **만들어 보고 비교하는 쪽**을 택함.
- 이 방식이 성립하는 전제: **합칠 때 인터페이스가 맞아야 한다.** (§4 리스크 참조)

**배경 — 현재 구현 실태 (2026-08-01 확인)**

에이전트 시뮬레이션은 **저장소에 한 줄도 구현되어 있지 않다.**

| 확인 대상 | 실태 |
| --- | --- |
| `demo/finverse-simulation.html`의 타임라인 | **하드코딩된 배열 리터럴**. 생성 진행 UX도 `setTimeout` 한 줄 |
| `package.json` | LLM SDK 없음 (next · react · tailwind · lucide-react · pretendard) |
| `pyproject.toml` | `dependencies = []` |
| MiroFish / OASIS | 외부 저장소를 **코드 해부만** 한 상태([리포트](../MiroFish-코드해부-리포트.html)). 이 저장소와 연결된 적 없음 |
| `app/` | `layout.tsx` · `page.tsx` 2개뿐 |

→ 결정 #18(온디맨드 + 캐시)은 "매크로 agent 10~15 + 섹터 agent 9 × 라운드 5~8이면 감당 가능하다"는 **한 번도 측정한 적 없는 가정** 위에 서 있다. 이번 분산 프로토타입이 그 실측을 겸한다.

## 3. 준비했으나 이번 회의에서 다루지 않은 안건

브리핑 §7의 A/B/C 그룹은 **논의되지 않았다. 부결이 아니라 이월**이다. 다만 아래 표시한 것들은 **트랙이 진행되면 곧 막힌다.**

| 안건 | 상태 | 언제 막히나 |
| --- | --- | --- |
| **A-1** 섹터 9개 승인 (#15의 "7~8개" → 9개 조정 기록) | 이월 | 관계DB·그래프를 코드로 옮기는 시점 |
| **A-2** 관계DB 73행 검토 · 강도 실증 계획 · `regulates` 추가 여부 | 이월 | 같음 |
| **A-3** 이벤트 카드 선별 기준 (하루 몇 개 · 무엇을 매크로 관련으로 볼 것인가) | 이월 | **① 트랙의 "뉴스 수집" 착수 직후** |
| **A-4** 나 트윈 캐릭터 항목 + 무보유 유저 템플릿 포트폴리오 | 이월 | **③ 트랙 착수 직후** |
| **B-1** 대가 4인 엔터 수위 + 실명 사용 권리 | 이월 | V3 후반 |
| **B-2** 편향 판정에 "왜 그렇게 판단했나" 입력 포함 여부 | 이월 | V3 후반 |
| **C-1** 경량 시뮬 생성 시간·토큰 실측 → SLO | **결정 #21에 흡수** | — |
| **C-2** AGPL 의무 범위 법률 확인 | 이월 | 엔진 선택이 굳는 시점 |
| **C-3** 간접 경로(2-hop) 전파 규칙 | 이월 | 섹터 충격 계산 구현 시점 |

**가장 먼저 필요한 것은 A-3과 A-4다.** ①·③ 트랙이 착수하자마자 각각 이 결정을 요구한다.

## 4. 리스크 — "합칠 때"

결정 #21의 방식은 착수 속도를 벌지만, **통합 시점의 재작업 위험**을 만든다. 세 사람이 각자 만든 시뮬이 서로 다른 모양의 결과를 뱉으면 합칠 수 없다.

**완화책 — 방식은 각자, 계약은 공통.**

지금 합의가 안 된 것은 **"어떻게 만드나"**이지 **"무엇을 뱉나"**가 아니다. PRD §6.3의 `EventSimulation` 스키마를 **각자 프로토타입의 출력 형식으로 먼저 못 박으면**, 내부 구현이 달라도 합칠 수 있다.

```jsonc
{
  "cacheKey": "카드 id @ BaseModel 날짜",
  "timeline":     [ { "t", "actor", "text", "activatedRelations": [], "sentiment" } ],
  "sectorImpact": { "sec-xxx": { "sign": ±1, "strength": "weak|mid|strong" } },
  "forecast":     { "paths": { "optimistic|base|risk": { "rangePct": [lo, hi] } } },
  "provenance":   { "agentCount", "rounds" }
}
```

- 이 중에서도 **`sectorImpact` 하나가 임계점**이다. ③ 나 트윈이 소비하는 유일한 입력이고(연결 조인트 #2), 이게 맞으면 나머지가 달라도 화면은 붙는다.
- 각 프로토타입은 **생성 시간과 토큰 소비를 기록**한다 (C-1 실측 겸용).

**비교 기준을 미리 정해 둘 것** — 합칠 때 "누구 것이 나은가"를 감으로 정하지 않도록: ① 생성 시간 ② 토큰 비용 ③ 타임라인이 관계DB를 실제로 인용하는가 ④ 같은 입력에 같은 출력이 나오는가(재현성).
